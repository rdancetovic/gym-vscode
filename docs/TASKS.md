## Implementation and test evidence

These notes record observed implementation/test evidence only; they do not approve or change task status.

| Task | Observed evidence |
|---|---|
| API-01 | Java catalogue/domain classes represent all four classes, prices, 12 session IDs/times, capacity and initial availability. Participant validation and totals are covered by 58 passing Java assertions. |
| API-02 | `ReservationStateStore` initializes/loads `data/reservations.json`, persists reservations/statuses/availability and restores saved state on reload. Initialization, load/save, restoration, and error handling are covered by 21 passing Java assertions. |
| API-03 | `POST /reservations` validates request JSON, returns a Confirmed reservation with code and price fields, updates availability, and saves before returning 201. Error/status validation, unchanged state on invalid input or persistence failure, code uniqueness/collision and exhaustion are covered by 51 passing Java assertions. |
| API-04 | `GET /classes` is registered on the existing Java server and returns all four catalogue classes and three sessions each, with required fields/types and live availability from `ReservationStateStore`. HTTP tests cover exact catalogue values, initial availability, persisted confirmed/cancelled state fixtures, HTTP 200/JSON content type, state/file non-mutation, unsupported methods (405 with `Allow: GET`), and non-exact/unknown paths (404). The API-04 suite passed 250 assertions; API-01/02/03 regression suites also passed 58/21/51 assertions in the same run. |
| API-05 | Compared the existing API-03 `POST /reservations` implementation and tests with all API-05 acceptance criteria and `REQUIREMENTS.md`. The implementation met the contract; no gaps were identified, and no source or test files were modified. Current-session verification passed API-01 (58), API-02 (21), API-03 (51), and API-04 (250) assertions; `git diff --check` passed. |
| API-06 | Extended the existing `ReservationApiHandler` to support `GET /reservations/{code}` while preserving POST. Lookup validates the exact `GYM-` plus six-digit format, returns all Reservation fields and the stored Confirmed/Cancelled status, and does not mutate state. HTTP tests cover both statuses, malformed and unknown codes, memory/file read-only behavior, and method/path behavior. Current run: 74 combined reservation-endpoint assertions passed; API-01 58, API-02 21, API-04 250 assertions passed; `git diff --check` passed. |
| API-07 | Extended the existing `ReservationApiHandler` to support `DELETE /reservations/{code}` while preserving POST and GET. Confirmed reservations are marked Cancelled, availability is restored, and state is persisted before returning HTTP 200; malformed, unknown, and repeat-cancel cases return the specified errors. Tests cover persistence, GET after cancellation, failed-operation state integrity, and persistence failure. Current run: 95 combined reservation-endpoint assertions passed; API-01 58, API-02 21, API-04 250 assertions passed; `git diff --check` passed. |
| Browser regression | The existing browser test page reported 112 passed and 0 failed when run through the server after API-02. It was not rerun after API-03; frontend source was unchanged. |
